# Demo privacy boundaries

- Each clinic has an independent SQLite file, API credentials, AES-256-GCM identity key, and HMAC pseudonym secret. Direct identifiers are encrypted as one identity record using a fresh 12-byte nonce and AAD bound to clinic, patient and schema version.
- The deterministic matcher uses clinic-local clinical facts. It never opens identity records. A selected identity is revealed only through an authorized clinic/patient demo route; access is audited without identity values.
- Exact identity leak detection uses keyed HMAC fingerprints and length-based comparisons, allowing the packet guard to check every seeded identity value without decrypting identity records. Contact, SSN and absolute-date patterns are also blocked in candidate content. Fixed routing metadata can contain its declared creation date.
- Sponsor packets contain only criterion-relevant evidence, age bands instead of exact ages, relative observation timing and per-trial pseudonyms. Sex is omitted unless a protocol requests it. Clinic display aliases, patient IDs, identity fields, clinical free text and absolute observation dates are excluded.
- PyNaCl sealed boxes protect these packets in hub storage. Only the sponsor process reads its private key. Sealed boxes do not authenticate the sender: independent API credentials authorize routing. Backends bind to loopback; local HTTP is a demo transport, not a production TLS deployment.
- Decline/withdrawal stops local evaluation and persists retractions for delivery, including when the hub is unavailable. A stale or superseded packet is retracted; fresh review is required before another is sent. Retraction cannot force an external recipient to forget information it already observed.
- If any nonzero aggregate cell is below the threshold, the entire row is suppressed to prevent subtraction from totals. The default of one is explicitly for fictional demo cohorts. This is not a formal disclosure-control guarantee.

This is process/data-flow separation on one developer machine, not OS sandboxing. A machine administrator could read all local files. Keys are in ignored `.keys/`, not an HSM; clinical facts remain plaintext inside clinic databases; demo patient selection is not production authentication. There are no real patients, EHR integrations, delivered notifications, or actual screening appointments. Do not expose these demo apps publicly or use real patient information. Production would require user authentication/RBAC, TLS, backup encryption, stronger audit/retention, consent/IRB and de-identification review. We do not claim anonymity or HIPAA compliance.
